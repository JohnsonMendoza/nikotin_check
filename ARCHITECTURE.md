# Архитектура бота «Дыши свободно»

Документ для пояснительной записки и защиты курсового проекта.
Проект: «Факторы распространённости потребления никотина в молодёжной среде»,
подход «Обучение служением», СПбГТИ(ТУ). Заказчик — социально-психологическая лаборатория вуза.

---

## 1. Назначение и границы продукта

**Продукт:** анонимный Telegram-бот самопомощи для студентов 18–25 лет, которые употребляют
никотинсодержащую продукцию (вейпы, сигареты) и хотят прекратить или сократить потребление.

**Четыре функции:** трекинг дней без никотина и сэкономленных денег; разоблачение мифов;
экстренная помощь в момент тяги; навигация к реальной помощи.

**Чем бот не является:** медицинской услугой, средством диагностики, назначением лечения,
заменой психолога или нарколога. В интерфейсе это сказано прямо (`/help`), а тексты выдержаны
в нейтральном тоне без запугивания и без осуждения за срыв.

## 2. Связь исследования и продукта (главное для защиты по социологии)

Продукт не «придуман», а выведен из данных опроса (N≈100+). Каждая функция — ответ на конкретный вывод.

| Вывод опроса | Функция бота | Механизм воздействия (поведенческая логика) | Что измеряем |
|---|---|---|---|
| Устойчивые мифы о «безопасности» вейпов («просто пар», «без никотина безопасно») | `/myths`: 5 карточек «Миф → Факт» с источниками | Коррекция нормативных убеждений; формат «сначала миф, потом факт» снижает защитную реакцию | Число открытых карточек, доля дошедших до 5-й, ответ q2 анкеты |
| Стресс — главный триггер потребления | `/sos`: дыхание 4-7-8, правило 10 минут, вода, прогулка | Замена инструмента саморегуляции: тяга рассматривается как волна (3–5 мин), а не как команда | Число SOS-сессий, доля завершённых практик, самооценка «отпустило», q1 анкеты |
| Высокий запрос на анонимный цифровой формат поддержки | Псевдонимный профиль, informed consent, `/delete`, отсутствие персональных полей | Снижение барьера обращения (страх огласки в вузе) | Доля давших согласие, retention D7/D30 |
| Недооценка расходов и дозы («один под — это ничего») | Счётчик сэкономленных денег + проекция на месяц/год | Материализация абстрактного вреда, обратная связь о выгоде | Средний заявленный расход, динамика счётчика |
| Срыв воспринимается как личный провал | `/reset` без осуждения + фиксация триггера | Профилактика эффекта «нарушенного воздержания» (abstinence violation effect); срыв как данные | Число сбросов, распределение триггеров |
| Запрос на поддержку, а не на контроль | Ежедневное утреннее сообщение, отключаемое в `/settings` | Поддерживающая обратная связь, автономия пользователя | Доля включённых уведомлений, отток после уведомлений |

Дополнительно бот сам собирает **обезличенные данные для второго витка исследования**:
триггеры срывов (`relapses.trigger`) и мини-анкета из 3 вопросов (`feedback`).
Это превращает продукт в инструмент мониторинга, а не только инструмент вмешательства.

## 3. Технологический стек и обоснование выбора

| Слой | Технология | Почему так |
|---|---|---|
| Язык | Python 3.11+ | знаком студенту, богатая экосистема, читаемый код для учебной работы |
| Telegram-фреймворк | **aiogram 3.x** (закреплено `>=3.13,<3.29`) | асинхронный, роутеры и типизированные `CallbackData`, встроенная FSM; версия ограничена, т.к. aiogram 3.33+ не импортируется на Python 3.11 |
| Хранение | **SQLite** через `aiosqlite` | ноль администрирования, один файл, легко приложить к работе; достаточно для сотен пользователей |
| Планировщик | **APScheduler 3.x** (`AsyncIOScheduler`) | ежедневная рассылка по cron и разовые задачи (таймер 10 минут) в том же процессе |
| Конфигурация | `python-dotenv` + `config.py` | токен вне кода, один модуль настроек, лёгкий перенос на хостинг |
| Транспорт | `polling` (локально/VPS) или `webhook` (aiohttp; Flask-адаптер для PythonAnywhere) | бесплатные хостинги дают только web-сервис, поэтому нужен второй режим |
| Проверка | `selftest.py` — собственный офлайн-харнесс на подмене транспорта | 71 проверка без токена и интернета: воспроизводимость на защите |

Отказ от более тяжёлых решений осознан: PostgreSQL, Redis, Docker, ORM и микросервисы
увеличили бы порог входа и не нужны при N в десятки-сотни пользователей.

                       │                                                     └───────────┬────────────┘
                       │            (PythonAnywhere: pa_wsgi.py = Flask + asyncio-поток)  │
                       └───────────────────────────┬──────────────────────────────────────┘
                                                   ▼
                                    ┌──────────────────────────────┐
                                    │  Dispatcher (aiogram)        │
                                    │  FSM: MemoryStorage          │
                                    │  порядок роутеров:           │
                                    │  navigation → sos → myths →  │
                                    │  feedback → core →           │
                                    │  onboarding → fallback       │
                                    └───────┬──────────────┬───────┘
                                            │              │
                        ┌───────────────────▼───┐      ┌───▼──────────────────┐
                        │      handlers/*.py    │      │     scheduler.py     │
                        │  сценарии диалога     │      │ APScheduler:         │
                        │  (что делать)         │      │ • cron каждый час :00│
                        └───┬─────────┬─────────┘      │ • разовый таймер 10м │
                            │         │                └───┬──────────────────┘
              ┌─────────────▼──┐   ┌──▼──────────────┐       │
              │   content.py   │   │    utils.py     │       │
              │ ВСЕ ТЕКСТЫ     │   │ расчёты и сборка│       │
              │ (контент)      │   │ текстов         │       │
              └────────────────┘   └────────┬────────┘       │
                                            │                │

Ключевой принцип: **контент отделён от логики**. `handlers/` не содержит формулировок —
они берутся из `content.py`; расчёты и подстановка значений — в `utils.py`.
Поэтому социолог (заказчик) может править тексты, не касаясь кода сценариев.

## 5. Основные потоки

### 5.1. Онбординг (FSM)

```
/start ──► WELCOME + ANONYMITY + CONSENT_ASK
            │
            ├─ «Не согласен» ──► в БД не пишется ничего; доступны /sos, /myths, /help
            │
            └─ «Согласен» ──► INSERT users(consent=1)
                                 │
                                 ├─ режим quit  ──► дата отказа (кнопка или ДД.ММ.ГГГГ)
                                 └─ режим watch ──► дата начала наблюдения = сегодня
                                 │
                                 ▼
                            расход в день (кнопка или число, 0…20000)
                                 ▼
                            час утреннего сообщения (или «без напоминаний»)
                                 ▼
                            ONBOARD_DONE + нижнее меню
```

Состояния FSM (`Onboarding.quit_date`, `.cost`, `.notify_hour`) нужны только для шагов
со свободным вводом. Кнопки нижнего меню обрабатываются первым роутером и сбрасывают
состояние — пользователь не может «залипнуть» в середине настройки.

### 5.2. SOS-практика (асинхронный ведущий)

```
/sos ──► SOS_INTRO ──► [▶️ Начать дыхание]
                          │  создаётся asyncio.Event (флаг «Стоп»)
                          ▼
             для цикла 1..SOS_CYCLES (6):
                 для фазы (вдох 4 с → задержка 7 с → выдох 8 с):
                     edit_message_text(фаза, подсказка, индикатор ●●○)
                     await wait_for(stop.wait(), timeout=секунды × SOS_TIME_SCALE)
                     если «Стоп» → выход из обоих циклов
                          ▼
             SOS_DONE (или SOS_STOPPED) + 3 приёма + случайный дополнительный
                          ▼
             [⏳ Таймер 10 минут] → APScheduler DateTrigger → сообщение через 600 с
             [👍 Отпустило] / [😣 Всё ещё тянет] → поддержка или повторный круг
```

Практика редактирует **одно** сообщение (не спамит), занимает ~2 минуты реального времени
и не блокирует других пользователей: ожидание — `asyncio.sleep`, а не `time.sleep`.
`SOS_TIME_SCALE` позволяет прогнать практику за ~6 секунд на демонстрации.

### 5.3. Ежедневная рассылка

```
APScheduler CronTrigger(minute=0)  ──► send_daily_notifications(bot, hour=now.hour)
                                          │
   SELECT users WHERE consent=1 AND notify_enabled=1 AND notify_hour=?
                 AND (last_notify_day IS NULL OR last_notify_day != today)
                                          │
                    для каждого: текст дня (ротация DAILY_MESSAGES) + цифры
                                          │
                    UPDATE last_notify_day=today  (защита от дублей)
                                          │
                    если days ∈ {7, 30} и анкета не заполнена → приглашение к анкете
                                          │
                    TelegramForbiddenError (бот заблокирован) → notify_enabled=0
                    TelegramRetryAfter → пауза и одна повторная попытка
```

Альтернативный вход — `GET /cron/<CRON_KEY>?hour=9` для внешнего планировщика
(cron-job.org, UptimeRobot). Это нужно на бесплатных хостингах, где процесс засыпает
или фоновые задачи недоступны. Дубли исключены полем `last_notify_day`.

### 5.4. polling vs webhook

| | polling | webhook |
|---|---|---|
| Кто инициирует соединение | бот → Telegram | Telegram → бот |
| Нужен публичный HTTPS | нет | да |
| Где работает | ноутбук, VPS | Render, PythonAnywhere, любой web-хостинг |
| Планировщик | внутренний APScheduler | внутренний + внешний cron через `/cron` |
| Особенность | конфликт при двух экземплярах | нужен секретный путь (в коде — хеш токена) |

## 6. Модель данных

Одна таблица на сущность, никаких персональных полей.

**users** — профиль и настройки

| Поле | Тип | Смысл |
|---|---|---|
| `user_id` | INTEGER PK | псевдоним из Telegram, единственный идентификатор |
| `consent` | INTEGER | informed consent (0/1); без него данные не пишутся |
| `mode` | TEXT | `quit` (отказ) / `watch` (наблюдение) |
| `quit_date` | TEXT (ISO) | первый день без никотина / начало наблюдения |
| `daily_cost` | REAL | расход в день, ₽ (для счётчика сэкономленного) |
| `notify_enabled`, `notify_hour` | INTEGER | утренние сообщения и их час |
| `relapse_count` | INTEGER | число сбросов счётчика (попыток) |
| `last_notify_day` | TEXT | защита от повторной рассылки за сутки |
| `feedback_done` | INTEGER | заполнена ли анкета |
| `created_at` | TEXT | момент согласия (UTC) |

**clean_days** (`user_id`, `day`) — отметки «сегодня без никотина» в режиме наблюдения;
первичный ключ по паре исключает двойной зачёт дня.

**relapses** (`id`, `user_id`, `day`, `trigger`) — обезличенная история срывов;
`trigger ∈ {stress, company, boredom, alcohol, habit, other}` — прямо проверяет вывод опроса о стрессе.

**feedback** (`user_id` PK, `q1`, `q2`, `q3`, `created_at`) — анкета:
`q1` — польза при тяге (1–5), `q2` — что полезнее (категория), `q3` — свободный текст (≤500 символов,
с фильтром на длинные числовые последовательности, чтобы не сдать телефон).

**Правила счёта (важно для корректности выводов):**
`days = today − quit_date` в полных сутках, дата отказа = день 0;
`money = days × daily_cost` — оценка, а не бухгалтерия; в режиме наблюдения
деньги считаются от числа отмеченных «чистых» дней, а не от дней наблюдения.

**Производные данные для отчёта:** `db.all_stats()` → агрегаты (среднее, медиана, максимум,
распределения триггеров и ответов); `db.export_feedback_csv()` → CSV **без** `user_id`.

## 7. Анонимность, приватность и этика

1. **Минимизация данных.** Только то, что нужно функциям: псевдоним, дата, сумма, настройки,
   отметки, триггеры, анкета. Ни имён, ни username, ни телефонов, ни текстов переписки.
2. **Псевдонимизация, а не анонимность.** В тексте согласия это сказано прямо: `user_id` —
   устойчивый псевдоним; обещать «абсолютную анонимность» было бы некорректно.
   В пояснительной записке термин стоит употреблять так же.
3. **Informed consent до первой записи.** До нажатия «Согласен» в базе нет ни одной строки.
   Отказ не блокирует SOS, мифы и контакты помощи.
4. **Право на удаление.** `/delete` физически удаляет строки из всех четырёх таблиц.
5. **Агрегация вместо персонализации в отчёте.** `/stats` и `/export` не содержат идентификаторов;
   в записку идут только доли и средние.
6. **Приватность по умолчанию.** Роутеры принимают только личные чаты (`F.chat.type == "private"`),
   в группах бот молчит.
7. **Логи.** Уровень INFO не печатает содержимое апдейтов; DEBUG на боевом запуске запрещён.
8. **Ненасильственная коммуникация.** Срыв описан как нормальная часть процесса; нет стыда,
   нет «страшилок», факты сформулированы с указанием границ знания («данных за 30–40 лет нет»).
9. **Границы компетенции.** Бот не диагностирует и не назначает лечение; `/help` ведёт к
   психологу вуза, федеральной линии 8-800-200-0-200 и врачу.
10. **Что стоит согласовать с заказчиком до пилота:** формулировки фактов, контакт психолога,
    текст согласия, план реагирования, если студент напишет о тяжёлом состоянии.

## 8. Метрики оценки продукта (что писать в раздел «результаты»)

| Метрика | Как считается из данных бота | Зачем |
|---|---|---|
| Конверсия в согласие | `consented / users` | приемлемость формата и доверие к анонимности |
| Активация | доля профилей с заполненной датой и расходом | понятность онбординга |
| Retention D7 / D30 | доля пользователей с активностью через 7/30 дней | удержание (нужен журнал активности — см. ограничения) |
| Средняя длительность серии | `avg_days`, `median_days`, `max_days` из `/stats` | основной поведенческий исход (self-report) |
| Число срывов на пользователя | `relapses / consented` | нормализация срыва как части процесса |
| Распределение триггеров | `relapses.trigger` | проверка вывода «стресс — главный триггер» |
| Полезность компонентов | `feedback.q2` | что развивать в v2 |
| Субъективная помощь при тяге | `feedback.q1` (1–5) | оценка SOS |
| Доля «чистых» дней в режиме наблюдения | `clean_days / дней наблюдения` | эффект постепенного сокращения |

**Важная оговорка для записки:** все исходы — самоотчёт. Биохимической верификации
(котинин, CO-монитор) нет, контрольной группы нет, выборка самоотбора (бот открывают
мотивированные студенты). Поэтому корректные формулировки — «связано с», «по самоотчётам»,
а не «бот доказанно снижает потребление». Дизайн оценки — пилотное исследование
feasibility/acceptability, а не RCT.

## 9. Ограничения MVP (честный список)

1. **Самоотчёт и предвзятость самоотбора** — см. выше.
2. **Retention не считается автоматически:** журнал активности не ведётся (сознательная
   минимизация данных). Для D7/D30 нужно добавить обезличенный счётчик активных дней.
3. **FSM в памяти** (`MemoryStorage`): при перезапуске незавершённый онбординг сбрасывается,
   сохранённые данные не теряются — пользователь просто проходит `/start` заново.
4. **Задачи APScheduler в памяти:** таймер на 10 минут не переживает перезапуск процесса.
5. **Один процесс + SQLite:** горизонтальное масштабирование не предусмотрено;
   для тысяч пользователей нужен PostgreSQL и постоянный jobstore.
6. **Нет шифрования at-rest:** файл БД защищён только правами ОС; на бесплатном Render
   он ещё и стирается при перезапуске (поэтому там только демо).
7. **Webhook на бесплатном PythonAnywhere:** один воркер и периодические перезагрузки —
   длинная SOS-практика может оборваться.
8. **Нет модерации свободного текста:** есть только эвристика на числовые последовательности;
   студент теоретически может сам написать себя опознаваемо.
9. **Мифы о вейпинге опираются на быстро меняющуюся доказательную базу** — тексты нужно
   пересматривать раз в семестр вместе с заказчиком.

## 10. Куда развивать (v2, для раздела «перспективы»)

* Обезличенный журнал активности → корректные retention-метрики и графики для лаборатории.
* Персонализация SOS по триггеру: «стресс» → дыхание, «компания» → сценарии отказа,
  «скука» → короткие активности.
* EMA-опросы (ecological momentary assessment): 1–2 коротких вопроса в день о тяге и контексте —
  превращает бота в инструмент сбора социологических данных.
* Веб-панель для лаборатории с агрегатами (без доступа к персональным срезам).
* PostgreSQL + постоянный jobstore + Redis для FSM; Docker-образ.
* A/B-тест формулировок мифов и утренних сообщений на обезличенных метриках.
* Модуль «сокращение потребления» для тех, кто не готов к полному отказу (harm reduction).
* Многоязычность и адаптация под другие вузы (контент уже вынесен в один файл).

## 11. Как проверялась работоспособность

`selftest.py` — офлайн-харнесс: транспорт Telegram подменён «фальшивой сессией»,
апдейты подаются через `Dispatcher.feed_update`, нажатия кнопок ищутся в реальных клавиатурах.
**71 проверка**, 13 групп:

1. онбординг и согласие (в т. ч. «до согласия в БД ничего нет»);
2. трекер и расчёты (дни, деньги, проекции, склонения, отбраковка дат);
3. все 5 карточек мифов + источники;
4. SOS: 18 фаз дыхания, 3 приёма, таймер, поддержка;
5. срыв: тон текста, перезапуск счётчика, фиксация триггера;
6. режим наблюдения и защита от двойной отметки дня;
7. анкета: 3 вопроса, повторное прохождение, отбраковка телефона в тексте;
8. помощь, настройки, админ-сводка без `user_id`;
9. рассылка: отправка, защита от дублей, чужой час;
10. анонимность схемы БД, обезличенность CSV, полное удаление по `/delete`;
11. устойчивость к исключению в обработчике;
12. целостность контента (5 мифов, 3 приёма, длительность практики, ≥7 утренних сообщений);
13. режим webhook: HTTP-сервер, приём апдейта, `/health`, защита `/cron` ключом.

Артефакт прогона — `demo_transcript.txt`: полная стенограмма диалога, пригодная как
приложение к курсовому («демонстрация практического продукта»).
